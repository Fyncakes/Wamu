WAMU — UGANDA-FIRST MESSAGING PLATFORM
Product Requirements & Technical BlueprintVersion 1.0 • Chat-first strategy • Android-first
1. Executive Summary
Wamu is a Uganda-first communication platform designed to provide the core everyday messaging experience people expect from modern messaging apps while adding features that make the service particularly useful for Ugandan users and communities.
The first release should NOT attempt to launch the entire Wamu super-app. The product should first win trust and daily usage through excellent private messaging, media sharing, voice/video calling, groups, communities, status, contacts and notifications. Business, marketplace, payments, delivery and AI capabilities can then be layered on top of the communication network.
2. Product Vision
Positioning: “Wamu — Uganda’s digital communication home.”
Long-term loop: Connect → Chat → Share → Discover → Do more.
Phone-number-based onboarding with OTP verification.
Fast private and group messaging.
Photo, video, audio/voice-note and document sharing.
Voice and video calls.
Status/stories.
Groups and communities.
Strong privacy and security.
Low-data and unreliable-network resilience.
Uganda-focused discovery and community features.
Future expansion into business messaging, commerce, payments and AI.
3. Product Strategy
The goal should not be to copy WhatsApp's source code, branding, proprietary assets or private implementation. Wamu should independently implement a comparable category feature set with its own design, identity, architecture and user experience.
WhatsApp's current feature set demonstrates why privacy, media messaging, groups, communities, status and calling are foundational expectations. Its documentation states that personal messages, calls, voice messages, photos, videos and documents are protected by end-to-end encryption. Wamu should treat comparable privacy as a core engineering requirement rather than an optional later feature.

9. Message Model
A message should contain metadata such as message ID, conversation ID, sender ID, message type, timestamps, reply-to ID, forwarding metadata and delivery/read state. For encrypted private conversations, the server should store ciphertext and routing metadata rather than plaintext message content.
10. Media Architecture
Recommended flow:
Client requests an upload authorization/token.
Backend validates authenticated user and intended conversation.
Client uploads encrypted media to object storage.
Backend stores a media-object record and encrypted message metadata.
Recipient receives a real-time message event.
Recipient downloads the media securely using an authorized mechanism.
Client decrypts and displays/plays the media.
Background workers create safe thumbnails/transcoding derivatives where the security model permits.
Do not store large media blobs directly inside PostgreSQL. Store media in object storage and keep metadata/reference records in PostgreSQL.
11. Security & Privacy
End-to-end encryption should be designed before production launch for private chats and calls.
Use a mature, independently reviewed cryptographic protocol/library rather than inventing encryption.
Never invent a custom encryption algorithm.
Never log plaintext messages, OTPs, access tokens or private media keys.
Hash refresh tokens before database storage.
Rate-limit OTP requests, login attempts and suspicious activity.
Use short-lived access tokens and revocable sessions.
Encrypt data in transit with TLS.
Protect object storage with private buckets and controlled access.
Use server-side authorization for every conversation/group operation.
Provide block/report tools.
Build abuse/spam controls from the beginning.
Maintain audit trails for administrative/security actions.
WhatsApp documents end-to-end encryption for personal messages, calls, voice messages, photos, videos, documents and related private content. Wamu should set an equally serious privacy target for personal communication. See WhatsApp's official privacy and encryption documentation for the feature baseline.
12. Real-Time Messaging Flow
Flutter → authenticated WebSocket → message service → authorization → persist encrypted message metadata/ciphertext → publish event → recipient WebSocket → delivery receipt → read receipt → push notification if recipient is offline.

20. Development Phases
Phase 1 — Foundation: FastAPI, PostgreSQL, Redis, migrations, authentication, users, devices, sessions, CI/CD, health checks.
Phase 2 — Messaging: Conversations, members, text messages, WebSockets, receipts, typing, presence, push notifications.
Phase 3 — Media: Photo, video, audio, voice notes, documents, object storage, thumbnails, compression, resumable uploads.
Phase 4 — Groups & Communities: Groups, roles, invites, announcements, polls, communities, moderation.
Phase 5 — Calls: WebRTC signaling, one-to-one voice/video calls, call history, TURN.
Phase 6 — Privacy & Security: E2EE implementation, device/session security, abuse controls, encryption verification, audits.
Phase 7 — Beta: Performance testing, low-network testing, crash monitoring, closed Uganda beta.
Phase 8 — Public Launch: Play Store release, onboarding, referral system, support, monitoring and controlled scaling.
Phase 9 — Wamu Expansion: Business profiles, local discovery, marketplace, payments, events and AI.
21. Performance Targets
Fast chat screen startup on budget Android devices.
Message send should feel immediate even when network quality is poor.
Messages should be queued locally when temporarily offline.
Media should adapt to connection quality and user-selected data mode.
Backend should be horizontally scalable.
WebSocket connections should be monitored and recover automatically.
No single server should be a permanent state dependency.

25. Important Engineering Decision
Do not build every feature at once. Build a vertical slice first: register → find/contact a user → open chat → send text → receive text → delivery/read receipts → push notification. Then add photo/video/audio/files, followed by groups, status and calls.

28. Final Direction to the Development Team
Build Wamu as a serious communication platform first. The objective is not merely to make another chat UI; it is to build a reliable communication network capable of handling private messages, groups, media, calls, communities and local discovery at scale.
The application must be designed for Uganda's real-world constraints: Android-first usage, mobile data costs, variable network quality, budget devices, phone-number identity and strong community usage. Privacy and security must be designed into the architecture from the beginning.
Once Wamu becomes a trusted communication layer, the same identity, social graph, groups and business relationships can power the broader Wamu ecosystem.
29. Reference Baseline
The product team should use current messaging-platform capabilities as a feature benchmark, but implement Wamu independently. WhatsApp's official documentation currently describes end-to-end encrypted personal messages/calls, voice messages, photos, videos, documents, groups, communities, status and related privacy controls. Wamu should aim for comparable quality and privacy while maintaining its own product identity and architecture.
